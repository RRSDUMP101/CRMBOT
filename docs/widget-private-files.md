# Private files in website chat

Apply append-only migration `040_widget_attachments.sql` before deploying. Set `WEB_CHAT_ATTACHMENTS_ENABLED=true` to enable the widget/full-page upload control and staff website-chat replies. Default is off. Files stay in the existing private R2 bucket; there are no public file URLs or provider sends.

Visitors select a PDF, JPEG or PNG of at most 5 MiB, then confirm sending. Images use the existing validated color-image container formats. The widget sends its partitioned visitor cookie with `X-RRS-Widget: 1`; full-page chat uses its separate web visitor cookie. Downloads require the same active session and conversation, or an active staff session in that organization. The API checks those permissions again after slow storage operations. Responses use `private, no-store`, `nosniff` and attachment download disposition. Widget downloads use a short-lived local Blob URL after an authenticated fetch; it is revoked after download.

The upload API is `POST /api/chat/attachments` with raw bytes, `Content-Type`, URI-encoded `X-File-Name` and UUID `X-Client-Id`. GET on the collection returns capabilities; GET on `/:id` downloads one committed file. Reusing the same client ID with identical bytes/metadata returns the same file/message; different bytes are rejected. Widget prechat consent and enabled state remain enforced.

Staff use `/api/admin/conversations/:conversationId/web-attachments` with the same headers plus `X-Conversation-Version`. Sending requires the exact current human assignee, conversation version and customer message sequence before and after upload. Session revocation, reassignment or new customer input blocks a stale send. Metadata and private download controls appear in the inbox; customer-visible replies appear in both web chat views.

A customer file atomically creates a canonical user message, unread sequence, attachment reference and durable Flow ingress. It interrupts an active AI generation and moves the conversation to staff review. The filename and bytes are not interpreted as chat keywords or AI input. Published web Flow actions run before basic team routing; a durable pending marker lets cron recover this ordering after a crash. Existing non-social Flow sending restrictions remain in force. Staff replies use canonical agent messages and never enqueue an external provider command.

The source hash, file metadata and message binding are immutable. Default quota is 100 MiB per organization, configurable with `WEB_CHAT_FILE_STORAGE_LIMIT_BYTES`; each conversation allows 20 MiB. Pending uploads expire after 15 minutes. Minute cron performs bounded cleanup with explicit D1/R2 bindings and retries failed deletions. Published files and their evidence are retained: no new automatic deletion policy is introduced. Ambiguous committed database responses never delete ready bytes; late storage writes after expiry retain a deletion retry marker until cleanup succeeds.

`tests/web-chat-attachments.test.ts` covers permissions, no-store access, idempotence, database/storage faults and Flow/routing order. `tests/widget-runtime.test.ts` exercises confirmation/retry and authenticated downloads in the widget script. Root release validation additionally runs the compiled Worker HTTP file tests. All test data is synthetic; device/browser QA and real visitor use are separate acceptance evidence.
